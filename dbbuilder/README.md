# dbbuild

One-time builder for a local D&D 5.5e (2024 rules) database, stored as plain JSON files.
Main source: https://dnd2024.wikidot.com. Node >= 20.

```
npm install
node src/cli.js <command>
```

## Pipeline

```
fetch / import-html  ->  data/rules-raw/dnd2024-wikidot/ (raw HTML cache)
build                ->  data/rules/       (final JSON; reads the cache only, never the network)
```

| Command | Network | What it does |
|---|---|---|
| `fetch` | yes (cache-first) | Class pages from the config, their subclass pages, and the multiclass page |
| `fetch <page-id...>` | yes (cache-first) | Specific Wikidot pages, such as `sorcerer:main` |
| `fetch catalogs [kind]` | yes (cache-first) | Catalog data (`spells`, `feats`, `equipment`, `backgrounds`, `species`, `monsters`) |
| `discover links <page-id>` | yes (cache-first) | List internal Wikidot page IDs linked from a page |
| `import-html <file> --title <page-id>` | no | Put a browser-saved page into the cache (use if the site blocks automated requests) |
| `inspect <page-id>` | no | Heading/table/fact outline of a cached page, to see what the extractor sees |
| `build` | no | Cache -> `data/rules/`, validation, `_reports/` |
| `status` | no | List cached pages |

A page is fetched at most once per cache key. Failures are never cached. To refetch a page, delete its file in `data/rules-raw/dnd2024-wikidot/`.
Requests are rate-limited (`delayMs`), send the `userAgent` from the config, and back off on 429/5xx.
The raw cache retains Wikidot page HTML and canonical page URLs.

## Output layout

```
data/rules/
  index.json                         manifest: classes/subclasses and catalog index paths
  classes/<class-id>/class.json
  classes/<class-id>/subclasses/<subclass-id>.json
  spells/index.json                  compact summaries; spells/<spell-id>.json details
  feats/index.json                   compact summaries; feats/<feat-id>.json details
  equipment/index.json               filterable summaries; equipment/<item-id>.json records
  backgrounds/index.json             filterable summaries; backgrounds/<background-id>.json records
  species/index.json                 filterable summaries; species/<species-id>.json records
  monsters/index.json                filterable summaries; monsters/<monster-id>.json combat records
  schema/class.schema.json, subclass.schema.json    JSON Schema the records were validated against
  schema/character.schema.json                      separate character-save contract
  schema/spell.schema.json, feat.schema.json, equipment.schema.json, background.schema.json, species.schema.json
  schema/monster.schema.json
  _reports/classes.json              per-class status, errors, warnings and choice-audit summary
  _reports/choice-audit.json         emitted structured/partial/manual choice records with provenance
  _reports/rejected/...              records that failed validation (never in classes/)
```

Everything under `data/rules/` is regenerated by `build`. Hand fixes belong in overrides, not in the output.

### Frontend catalogs

The root `index.json` exposes each catalog index path and record count. Catalog `index.json` files contain only the compact summaries used by tracker search and selection, sorted by name; each summary points to a stable, individually loadable detail record. The tracker lazy-loads full rules text when a selected rule needs it.

Spell records include a stable ID, level (0 for cantrips), school, machine-joinable class IDs and labels, casting time, range, components/materials, duration, concentration/ritual flags, description, and named effects. Feat records include category/source variants, named benefits, original prerequisite wording, and parsed minimum character level/ability-score requirements when present. Equipment records retain source table properties and provide normalized category/subcategory, cost in copper pieces, weight in pounds, weapon damage/properties/mastery, and armor class/strength/stealth fields when present; unrecognized source values remain available as raw strings. Every record includes source URL/publication provenance.

Background records normalize ability-score options, feat references, skill/tool proficiencies, and equipment alternatives. Species records expose creature type, size, walking speed where parseable, and named traits while preserving descriptive prose. Their indexes contain only the selection summaries used by the tracker.

Monster records are sourced separately from Aidedd. They contain encounter-oriented facts (CR/XP, AC, HP, speeds, abilities/saves, skills, senses, languages, habitats, and publication), named traits/actions, linked spell IDs, and extracted mechanics such as attack bonuses, reach/range, save DCs, damage/healing dice and averages, recharge, uses, Multiattack counts/substitutions, and spellcasting DCs/frequency-based spell lists. Every ability includes its full plain-text `description`; source HTML is not copied into generated records. Fetching the monster catalog retrieves the index and individual pages with a one-second delay between requests.

Spell class IDs use the same slugs as `classes/<class-id>/class.json`. Catalog filters are advisory when a field is unknown; source prose remains authoritative for nuanced eligibility.

### Class and character schemas

Schema version 6 class and subclass records include `choices[]` alongside readable feature descriptions. Each choice has a stable `id`, level, feature, prompt, and a `scope` (`build`, `progression`, `preparation`, or `runtime`), plus a fixed or progression-based selection count, explicit options or an `optionSource`, and an optional change rule. Conditional follow-ups use `dependsOn`; an option source may declare `merge: "union"` when its catalog is combined with fixed options. Frontends should not present `runtime` decisions as permanent character selections. Spell and feat option sources can resolve against these catalogs; other dynamic sources such as infusions or maneuvers still require application support. Readable feature prose remains authoritative where source wording or eligibility cannot yet be normalized safely.

Progression rows are `progression{1..20: {proficiencyBonus, values}}`. Every value is keyed by a normalized column ID and uses `{status, value, unit}`. `status` distinguishes `known` (including numeric zero), `not-applicable` (a dash in the table), and `unknown` (blank source cell); dice are represented as `{kind:"dice", count, sides}` rather than strings.

Class and subclass rule records contain no player selections or mutable resource counters. Choice records retain the legacy fields and add stable `featureId`, `levelContext`, count bounds/distinctness, dependencies, prerequisites, replacement metadata, effects, provenance, and a `resolution` (`structured`, `partial`, or `manual`). Unresolved choices have no fabricated options and explain the extraction gap in `unresolvedReason`; clients should show the source feature prose and label these **Manual choice — rule details shown below**. Background, species, and feat records also expose a `choices` array. `_reports/choice-audit.json` inventories emitted choices and their resolution. The audit includes heuristic detection of choice-like class/subclass and catalog prose; it is a review aid, not a guarantee that every source sentence was detected. Catalog category coverage and spell-grant semantics remain incremental, so do not treat the current database as a complete executable character-creation model.

Choice options may include their own `effects` when the selected option changes character data. Background ability-score choices currently enumerate the seven legal allocations across the three listed scores; each selected option emits `ability-score-increase` effects with an ability, amount, and maximum score of 20. Consumers should apply only the effects on selected options and continue to display source prose.

Backgrounds that say to choose one kind of Artisan’s Tools, Gaming Set, or Musical Instrument expose an inline option list with a `proficiency-grant` effect for the selected tool. Other tool-choice wording remains manual until its candidate set is known.

Feat benefits with an explicit ability-score increase expose one selection per eligible ability and an `ability-score-increase` effect. When eligibility depends on another feat’s spellcasting ability or the character’s saving-throw proficiencies, the generator preserves that dependency in a partial choice and names the required `optionSource` rather than guessing a fixed list.

A saved character is a separate document validated by `schema/character.schema.json`; it references class/subclass IDs, stores selected choice option IDs, and keeps mutable hit points and resource counters in its own `state` object. The character schema does not yet enforce that a selected option is eligible or that selection counts match a build's class levels; the application must resolve `choiceId`, evaluate `countRule`, enforce prerequisites, and validate option IDs. The database builder emits the schema but does not create or mutate character saves.

`spellcasting`: `{ability, spellList, type: full|half|third|pact|other, cantripsKnownByLevel, preparedSpellsByLevel, spellsKnownByLevel, slotsByLevel{level:{spellLevel:count}}, pactSlotsByLevel{level:{slots, slotLevel}}}`.
Abilities are `str|dex|con|int|wis|cha`.

## Source and configuration (`config/dnd2024-wikidot.json`)

Wikidot is the sole configured source. Class page IDs are mapped in `classes.titles`; linked subclass pages are discovered from the level-three subclass feature and the class page’s subclass catalog. `multiclass.page` points at the Wikidot multiclassing rules. The cache and generated output are both configured to the project’s primary database paths.

The imported sites are unofficial references, not authoritative rules publishers. Records retain source page URLs, fetch times, and stated publications when available. The Wikidot source includes content beyond the core 2024 Player’s Handbook, including later releases, playtest material, and homebrew; verify provenance and suitability before presenting an option as core. Monster ability descriptions are retained from Aidedd alongside structured combat facts; review each provider’s terms and the underlying rights before redistribution.

## The common intermediate format

Any source only has to produce a `Doc` (see `src/parse/htmlToDoc.js`): a tree of sections holding paragraphs, lists and tables, plus a flat map of `label -> value` facts. Wikidot class tables are native HTML, including Artificer’s split progression tables; the builder combines table data by class level instead of maintaining hand-transcribed image charts.
Every record carries `sources[]` (page, URL, fetch time) so the source page remains traceable.

## First-run workflow

1. `fetch sorcerer:main`, then `inspect sorcerer:main`. Check that the headings and tables look like what the extractor expects.
2. Adjust `config/dnd2024-wikidot.json` page IDs if the sites change. Run `fetch` for classes/subclasses and `fetch catalogs` for all catalogs; pass one kind (`spells`, `feats`, `equipment`, `backgrounds`, `species`, or `monsters`) to fetch only that dataset. The monster crawl is slower because it observes the configured Aidedd request delay.
3. `build`, read `_reports/classes.json`. Fix systematic problems in the extractor; fix one-off page quirks with overrides.
4. Add `data/rules-raw/` to `.gitignore`.

## What the extractor expects from a page

- Core traits as label/value pairs (a two-column table, infobox, bold labels in prose/lists, or "Label: value" lines): Primary Ability, Hit Die, Saving Throws, Skills (including labels such as `Skills (Choose 2)`), Weapons, Tool Proficiencies, Armor Training, and Starting Equipment. Armor and equipment can also be prose sections; equipment alternatives can use lowercase `(a)` / `(b)` list markers and shared items.
- One or more progression tables with a Level column; split tables are merged by level. Feature columns, Proficiency Bonus, resources, and spellcasting counts/slots are read from the page tables.
- Feature headings in either `Level N: Name` or `Nth Level: Name` form. Repeated feature levels (such as Ability Score Improvement's “again at levels …” text) are copied to those levels.
- Subclass features as level-prefixed headings. Bare subclass page titles are supported when those pages are linked from the class's subclass feature.
